# M0 spikes

Two assumptions in the design are unverified. Both must have a written result
here before M1 starts.

## Spike 1: local runtime

**Question.** Can local mode run the same Worker code on the user's machine
with no Cloudflare account, including the scheduler, the workflow and the
database, started by one command?

**How.** `bun run local` starts `wrangler dev` for `apps/pipeline` with local
persistence in `.bd-data/` and calls the scheduled handler on an interval.

**Pass criteria.**

- [x] Starts with no login and no network access to Cloudflare.
- [x] `/health` answers.
- [x] The scheduled handler creates a RunWorkflow instance and it completes.
- [x] A second tick in the same slot does not create a second run.
- [x] Data survives a restart (`.bd-data/`).
- [x] Works on macOS, Linux and Windows.
- [ ] Can be packaged so a user runs one command without cloning the repo.

**If it fails.** Extract runtime interfaces (database, blobs, orchestration,
scheduling) and add a native Bun implementation. Record this in a new ADR and
extend the milestones.

**Result (2026-11-21): works, not adopted.** The Workers runtime runs
locally through wrangler, as measured below. It is not used as the basis of
local mode because it makes Cloudflare's toolchain a requirement of running
locally. Local mode becomes a native Bun runtime with Cloudflare as an
adapter (ADR 0018, superseding 0004).

Run by `scripts/spike-local.ts` in the
`spike-local` workflow ([run 44876667747](https://github.com/daiyanze/breaker-delta/actions/runs/44876667747)),
wrangler 4.164.0, on `ubuntu-latest`, `macos-latest` and `windows-latest`.
5 of 5 automated checks passed on each OS. The "One command without
cloning" row was checked later, against the executable from #7
([run 44908706191](https://github.com/daiyanze/breaker-delta/actions/runs/44908706191)).

| Criterion | Linux | macOS | Windows | How it was checked |
| --- | --- | --- | --- | --- |
| No login, no Cloudflare network | pass | pass | pass | No credentials on any runner. On Linux the whole run is inside a network namespace with only loopback. |
| `/health` answers | pass | pass | pass | `GET /health` returns `ok: true` |
| Scheduled handler starts a run that completes | pass | pass | pass | The launcher calls `/__scheduled`; `/health` then shows the slot as `done` |
| Second tick in the same slot starts nothing | pass | pass | pass | `/__tick` twice; the second returns `started: false`, "slot already ran" |
| Data survives a restart | pass | pass | pass | Stop, start again, then read the `runs` table from the SQLite file with `wrangler d1 execute --local`: the run from before the restart is there |
| One command without cloning | pass | pass | pass | Since #7: the `downloaded` job unpacks the executable on a fresh runner, with no chmod, and runs every criterion against it from a temporary folder, with no `bun` on `PATH` |

Notes:

- Offline, wrangler logs "Unable to fetch the `Request.cf` object" on start
  and falls back to a placeholder. Harmless: nothing in the pipeline reads
  `request.cf`.
- `bunx` is not used: the launcher runs `bun x wrangler`, which also works
  where `bunx` is not on `PATH`.
- The `spike-local` workflow stays as a smoke test for local mode on three
  OSes. Since #7 it also runs every criterion against the built executable,
  from a fresh folder with no `bun` on `PATH`, and keeps the executables as
  workflow artifacts.

**One command without cloning.** Not met with wrangler: the user needs the
repository, `bun install` and `bun run local`. ADR 0018 answers it with one
executable per OS built by `bun build --compile`, met since #7. The
executables are CI artifacts for now; publishing releases is later work.

## Spike 2: source reachability

**Question.** Which fetch groups are reachable from Workers egress, and which
from a home network? The two can differ for sources that rate-limit by IP or
block datacenter traffic.

**How.**

- Home network: `bun run probe`
- Workers egress: deploy `apps/pipeline`, then
  `curl -H "authorization: Bearer $PROBE_TOKEN" https://<worker>/__probe`

The targets come from `apps/pipeline/src/sources/launch-groups.ts`: one URL per
launch fetch group (20 groups).

- [ ] Every fetch group has a row in the table below for both networks.
